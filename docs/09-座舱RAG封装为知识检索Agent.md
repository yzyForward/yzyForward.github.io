# 把 RAG 封装成知识检索 Agent：工具和 Agent 到底怎么选

> 智能座舱大模型落地实战系列第 9 篇。前面写了 RAG（知识底座）和多智能体，这篇讲它们怎么衔接——RAG 是做成"工具"给 Agent 调，还是封装成"知识检索 Agent"接入？这是我实际项目里纠结过的一个设计决策。

---

## 一、问题：知识底座怎么接入多智能体

RAG 知识底座做好了（分块、检索、精排、治理都有了），现在要把它接入"1 中枢 + N 领域"的多智能体平台。有两种接法：

- **做成 Tool（工具）**：各领域 Agent 通过 MCP 直接调检索接口。
- **封装成 Agent（知识检索 Agent）**：作为一个垂类 Agent，和其他领域 Agent 平级。

到底用哪种？

## 二、两种方案各自的优劣

### 方案 A：RAG 做成 Tool

- **优点**：简单直接、低延迟——Agent 一个函数调用就拿到检索结果，没有额外一跳。
- **缺点**：每个 Agent 都要知道"怎么检索"（参数怎么传、结果怎么用），检索逻辑散落在各 Agent 里；复杂多轮检索没法做。

### 方案 B：RAG 封装成知识检索 Agent

- **优点**：检索逻辑集中——查询改写、多轮检索、证据整理都放在知识检索 Agent 里，其他 Agent 只管说"给我 XX 的证据"，不用关心检索细节；升级检索只动这一个 Agent。
- **缺点**：多一跳（A2A 委派比 MCP 直接调工具多一次往返），延迟略高。

## 三、我的结论：底层 Tool + 上层 Agent 封装

答案是**两者结合，不是二选一**：

- **底层是 Tool**：知识底座通过 MCP 暴露结构化检索接口，这是"能力"。
- **上层是 Agent**：在中枢平台里，把它封装成**知识检索 Agent**，作为 N 个垂类 Agent 之一接入，这是"封装"。

一句话：**Tool 是能力，Agent 是封装。**

为什么这么设计？因为检索不只是"查一下"——还有查询改写、混合检索、精排、多轮检索、证据整理这些多步逻辑。这些逻辑放一个专门的 Agent 里更清晰，其他 Agent 只管办事。

## 四、按场景分流：简单走 Tool，复杂走 Agent

Agent 形式多一跳，座舱对延迟敏感，所以要按场景分流：

- **高频、简单检索**：直接走 Tool（MCP 直连），低延迟；
- **复杂、多轮检索**：走知识检索 Agent（A2A），强能力。

这样"低延迟"和"强能力"两头都顾上。

## 五、接入后带来的好处

把 RAG 封装成知识检索 Agent 后，几个实际好处：

1. **职责隔离**：车控、导航这些 Agent 只管办事，检索质量由知识 Agent 统一保障。
2. **可替换**：换 embedding、换精排模型，只改知识 Agent，不动其他 Agent。
3. **可追溯**：知识 Agent 走 A2A 统一回传"证据 + 出处"，比各 Agent 各调各的更规范、更好审计。
4. **知识更新解耦**：知识底座更新，只动知识层，不动编排层。

## 六、总结

可复用的三条：

1. RAG 接入多智能体，**底层用 Tool（能力）、上层封装成 Agent（封装）**，两者不矛盾。
2. 检索逻辑重（改写、多轮、证据整理），**值得用一个专门的知识检索 Agent** 集中管理。
3. 按延迟敏感度分流：**简单走 Tool、复杂走 Agent**。
