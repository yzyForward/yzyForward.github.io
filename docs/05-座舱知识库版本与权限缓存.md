# RAG 的版本管理、权限隔离和多级缓存：让知识库可控可回滚

> 智能座舱大模型落地实战系列第 5 篇，RAG 系列的收官。检索做准了，还得考虑三件工程上的事：知识更新了怎么办、不同角色看到的数据怎么隔离、高频查询怎么不重复算。这篇讲治理层。

---

## 一、版本管理：知识更新怎么不"新旧混检"

座舱知识是经常变的——功能改了、话术更新了、政策调整了。如果知识一更新就直接覆盖旧数据，就会出现"这次查到新条款、下次查到旧条款"的不一致。

我的做法是**版本化 + 原子切换**：

1. 新文档以**新版本（epoch）**入库，旧版本保留、标记为 superseded；
2. 检索时只查 `active` 版本；
3. 新版本验证通过后，把 `active` 指针**一次性切到新 epoch**，旧版本的向量副本删除。

关键在"**原子切换**"：切换是一个操作，不会出现中间态。要回滚也简单——把指针切回旧 epoch 就行。

## 二、权限隔离：越权内容从数据层就挡住

知识库里有些内容不是所有角色都能看的（不同部门、不同权限等级）。权限隔离如果只做在接口层，会有漏洞——上层漏了鉴权，数据就可能漏出去。

我的做法是**权限过滤下推**：把权限作为过滤条件，下推到检索请求里。**越权内容在召回过程中就被过滤掉，根本不进候选、不进上下文。**

这比"先召回再过滤"可靠得多。先召回再过滤有个隐蔽的坑：如果 Top-K 被越权内容占满，后过滤会把本可命中的可见内容**挤掉**，直接漏召回。下推则是在可见子集里召回，从根上解决。

## 三、多级缓存：高频查询别重复算

RAG 的耗时大头在向量编码、检索、精排。高频问题每次都从头算一遍，又慢又费钱。所以做**多级缓存**：

- **L1 进程内缓存**：最热查询，命中直接返回，零网络开销；
- **L2 候选缓存**：缓存中间候选，命中跳过向量编码和检索；
- **L3 语义缓存**：语义相近的查询命中同一结果，减少重复的相似检索。

### 缓存键为什么要带"权限指纹 + 版本"

这是 RAG 缓存最容易漏的一个点：**不同角色、不同知识版本查同一问题，结果可能不一样。**

如果缓存键只按问题文本，就会出现"低权限用户命中高权限用户的缓存"（越权）、或者"知识更新了还在命中旧缓存"（过时）。

所以缓存键要带上**权限指纹 + 版本号**，保证缓存是"隔离"的——谁查、哪个版本查，各是各的缓存。

## 四、踩过的坑

1. 版本切换不做原子：新旧混检，用户同一时刻查到两种答案。
2. 权限只拦接口、不拦检索：越权内容从缓存或检索层漏出。
3. 缓存键不带权限/版本：跨权限命中、旧版本命中，隐蔽且难查。

## 五、总结

治理层三件事，核心都是"**可控**"：

1. 版本化 + 原子切换，让知识**可更新、可回滚**。
2. 权限过滤下推，让越权内容**从数据层就挡住**。
3. 多级缓存 + 权限指纹版本键，让高频查询**快而不越权**。

到这里 RAG 系列就完整了：分块（父子块）→ 检索（混合 + 精排）→ 查询（改写 + 同义词）→ 防幻觉（缺证不作答）→ 治理（版本 + 权限 + 缓存）。下一篇开始讲多智能体。
