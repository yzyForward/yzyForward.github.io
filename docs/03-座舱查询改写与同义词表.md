# 查询改写 + 同义词表：用户口语和文档术语对不上怎么办

> 智能座舱大模型落地实战系列第 3 篇。分块、检索都调好了，但还有一个高频漏召回场景：用户说的词，和知识库里存的词，根本对不上。

---

## 一、问题：用户口语 vs 文档术语

RAG 检索靠的是"相似度"，但用户的问法和知识库的写法经常是两套语言：

- 用户说"**雨刮**"，知识库存的是"**雨刷**"；
- 用户说"怎么开天窗"，知识库存的是"天窗开启操作步骤"；
- 用户说"这个咋弄"，知识库存的是规范的功能说明。

词对不上，向量相似度自然低，召回就漏了。这是 RAG 上线后最常见的"召回率低"来源之一。

## 二、方案：两侧各管一头

我把它拆成两个问题，分两侧解决：

- **术语侧**：用**同义词表**，把功能别名、口语化说法归一到标准词——解决"词对不上"。
- **查询侧**：用 **LLM 做查询改写**，把口语化、不规范的问题改写成标准表述——解决"话说不规范"。

一个管"词的映射"，一个管"句的规范化"。

## 三、术语侧：同义词表怎么建

同义词表是一张"别名 → 标准词"的映射，比如：

```
雨刮 → 雨刷
开天窗 → 天窗开启
冷气 → 空调
```

建设流程：

1. 从车机功能说明、服务卡片里抽**标准词**；
2. 从真实用户日志里收集**别名、口语化说法**；
3. 人工审核对齐，避免把不同功能误归成一个。

作用就是：检索前把用户话里的别名替换成标准词，让它和知识库对齐，召回就命中了。

## 四、查询侧：LLM 改写

查询改写用大模型（我用的 Qwen2 系列）把用户的口语问题改写成规范表述。比如：

- "这个咋弄" → "如何操作"
- "那它呢"（带指代）→ 结合上文补全成"那全景天窗怎么开启"

改写后检索，召回率明显提升。

## 五、两个关键细节（最容易踩坑）

### 1. 改写只用于召回，判定用原文

这是最重要的一个坑。**改写后的查询只用来召回，但相关性判定（这个块到底相不相关）要用用户原文。**

为什么？因为改写会"美化"问题——用户问了个跟车无关的事，改写可能把它"洗"成域内问题，然后硬召回一堆车内知识，产生幻觉。用原文判定，能守住"这个问题本来就不属于我们"的边界。

### 2. 改写后和原查询双路召回、合并去重

改写有风险——万一大模型改错了呢？所以改写后的查询和原查询**各跑一路召回，结果合并去重**。改对了，改写路能补上原文漏掉的；改错了，原文路还能兜底，不至于全军覆没。

## 六、效果与取舍

查询改写 + 同义词表解决的是"口语和专业术语之间的鸿沟"。它不能单独扛大旗，但配合混合检索、精排，是召回率从 68% 到 90% 里很重要的一块拼图。

取舍点：改写会多一次 LLM 调用、多一点延迟。所以我对**高频、简单查询不做改写**（直接检索），只有"口语化重、检索召回低"时才触发改写，按需调用。

## 七、总结

可复用的三条：

1. **术语侧用同义词表、查询侧用 LLM 改写**，两头对齐。
2. **改写只服务召回，判定用原文**，防止把域外问题洗成域内。
3. **改写后和原查询双路召回**，防改写改错，原文兜底。
